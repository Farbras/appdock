# Удаление, исправление проблем и собственные установщики

Реализовано 10 ноября 2026 года в рабочей копии 0.2.3. Это описание изменений исходного кода, а не опубликованного выпуска.

## Массовое удаление

Откройте **Установленные**, отметьте конкретные экземпляры и нажмите **Удалить выбранные**. Поиск учитывает название, версию и издателя. В каждой строке доступны область и точная идентификация Windows. Перед запуском откроется общий план AppDock: версии, коды продуктов, экземпляры, известные зависимости каталога и необходимость участия в мастере / UAC. Поставьте отметку подтверждения и начните выполнение.

Обнаружение для удаления читает четыре раздела Uninstall: HKLM/HKCU, обычный и WOW6432Node. Оно не использует приблизительное сопоставление названий. Выбирается точная запись реестра, а команда WinGet получает `--product-code`, `--exact`, `--version`, `--scope`, `--source winget`. При совпадении кода продукта в нескольких записях одной области, отсутствии версии либо изменении записи запуск запрещён. Название может использоваться как подсказка навигации в каталог, но не как цель удаления. WinGet может отказать в сопоставлении пакета; обхода через строку UninstallString нет.

Каждое удаление — отдельная последовательная задача с журналом. Ошибка не блокирует независимые задачи. Отмена очереди отменяет ожидающие действия, работающий деинсталлятор продолжает работу. После выполнения повторно читаются экземпляры Windows. Отдельно сохраняются результат команды и свидетельство отсутствия (`evidence: absent`). Успешный код без подтверждённого отсутствия означает «Требуется действие», а не подтверждённое удаление. Даже отсутствие записи не проверяет все portable-копии и все оставшиеся файлы.

AppDock не очищает реестр, настройки и оставшиеся папки. Достоверно известные зависимости ограничены встроенными связями каталога; неизвестные связи не угадываются. Для неоднозначных и неподдерживаемых записей используйте **Параметры Windows → Приложения → Установленные приложения** и выберите нужную версию и область.

## Мастер «Программа не работает»

Откройте действие в строке установленного приложения, карточке обнаруженной программы или раскройте проблемную задачу очереди / истории. Мастер показывает выполненные проверки, подтверждённые проблемы, неизвестные результаты и ручные шаги. Для VS Code отметьте расширения, которые должны быть установлены; их зависимости учитываются автоматически.

Доступные планы:

- **Повторная проверка** — только проверка готовности, без установки.
- **Восстановление WinGet** — штатный `winget repair` для точного MSI-экземпляра с кодом продукта GUID, если установленный CLI подтверждает поддержку точных фильтров. MSI может запросить исходный пакет, мастер и UAC. Для EXE без проверенного рецепта восстановления автоматическое repair не предлагается.
- **Исправление PATH** — для скомпилированных адаптеров Python, Git и Node.js: найден абсолютный исполняемый файл, проверен его ответ `--version`, папка отсутствует в актуальном PATH. При обнаружении другой установки в PATH исправление не предлагается. Перед записью снова проверяются файл, папка и исходное значение пользовательского PATH. Системный PATH не меняется.
- **Восстановление расширений VS Code** — обычные индивидуальные задачи установки только отсутствующих выбранных расширений из доверенного каталога, с зависимостями и итоговой проверкой. Сам VS Code не переустанавливается.

Все планы требуют просмотра и отдельного подтверждения. После выполнения, включая ошибки команды, повторяется проверка готовности. Успешное выполнение команды не означает автоматически исправленную программу. Для неизвестных программ остаются ручные инструкции; универсального исполнения команд и автоматической переустановки нет.

Резервная копия PATH записывается и синхронизируется на диск до изменения. Она содержит исходное значение (включая отсутствие переменной), результат добавления и единственную добавленную запись. В мастере доступен план отмены добавления. Если PATH не менялся, восстанавливается исходное значение. При последующих правках удаляется только однозначно найденная добавленная запись, остальные записи сохраняются. Если запись отсутствует или повторяется, автоматическое восстановление блокируется. Старые терминалы после исправления нужно открыть заново.

Адаптер Python ищет проверенную ветку 3.12 и актуальный PATH. Git и Node.js проверяются в стандартных местах и PATH. Node.js имеет отдельный диагностический адаптер; это не добавляет установочный источник в доверенный каталог. Наличие рабочего CLI не доказывает исправность всех функций, плагинов и пользовательских проектов.

## Мои программы

Откройте **Мои программы → Выбрать локальный EXE или MSI**. Системный диалог выбирает файл; пути запуска и аргументы из JSON не принимаются. AppDock создаёт собственную копию, вычисляет SHA-256 и считывает доступные сведения: имя, размер, исходное расположение, версию, издателя из метаданных, статус Authenticode. MSI-сведения читаются через Windows Installer в режиме чтения базы, без установки.

Укажите название, описание и один из значков. Можно добавить ссылку в существующий личный набор или создать набор «Мои программы». Затем отметьте установщики, откройте план, прочитайте сведения о файлах и подтвердите запуск. Записи всегда имеют отметку **Добавлено пользователем** и хранятся отдельно от встроенного каталога.

Подпись отображается четырьмя разными результатами: подтверждена, отсутствует, недействительна, проверку выполнить не удалось. Это результат проверки Windows на момент чтения; данные CompanyName / Manufacturer сами по себе не подтверждают издателя. SHA-256 подтверждает неизменность байтов, а не доверие к издателю.

MSI запускается через системный `msiexec /i` с обычным интерфейсом и без автоматической перезагрузки. EXE открывается через ShellExecuteEx, без тихих ключей и произвольных аргументов. Поддержки тихих рецептов для собственных EXE в этой итерации нет. AppDock целиком не повышает права; запросы UAC принадлежат штатным установщикам.

Перед планом проверяется хеш управляемой копии, непосредственно перед запуском он проверяется повторно. На время запуска и ожидания открытый файловый дескриптор запрещает запись и удаление копии в Windows. Замена исходного файла после просмотра плана не влияет на запускаемые байты. Повреждённая или отсутствующая копия блокирует запуск; выберите локальный файл заново. После добавления исходный файл может отсутствовать.

Одинаковый SHA-256 использует существующую запись; повторный явный выбор также восстанавливает её отсутствующую или повреждённую копию. **Удалить запись** удаляет только запись и управляемый установщик, без удаления установленного приложения. Незавершённая задача блокирует удаление записи. Управляемые копии сохраняются для повторного использования до удаления записи. Осиротевшие копии после прерванного добавления очищаются при открытии раздела; файлы вне этой папки не затрагиваются.

В набор экспортируются только название и SHA-256. Пути, команды, аргументы и локальные ID запрещены и повторно проверяются Rust. После импорта кнопка **Выбрать локальный файл для …** требует явного выбора файла с совпадающим SHA-256 и нового просмотра плана. Импорт ничего не ставит в очередь автоматически. В смешанном наборе встроенные программы добавляются в обычный выбор, собственные подтверждаются отдельными планами после выбора файлов.

Успешный код неизвестного установщика сохраняется как завершение процесса, а не доказательство установленной и готовой программы. Некоторые EXE передают работу дочернему процессу и завершаются раньше. AppDock честно оставляет ручную проверку; не угадывает наличие программы по названию файла.

## Хранение и совместимость

В `%LOCALAPPDATA%\app.appdock.desktop` находятся `custom-apps.json`, `custom-installers/` и `path-backups/`. История и задачи используют прежние `queue.json`, runs и одноразовые планы с ограничением 10 минут. Новое необязательное поле задачи `operation` содержит типизированный снимок действия; старые задачи без него продолжают работать. Новые статусы: `removed`, `repaired`, `checked`. Наборы схемы 1/2 читаются как раньше; `customPrograms` — необязательный список инертных ссылок. Возврат к старой сборке с новой историей не поддерживается: перед откатом сохраните данные.

В браузере всегда действует деморежим. В нём доступны виртуальные установленные экземпляры, PATH, копии, собственный EXE, наборы, удаления и мастер. Новые действия деморежима не вызывают нативный IPC. Rust также блокирует системное выполнение и возобновление при включённом деморежиме и сбрасывает неподтверждённый план при смене режима.

## Проверка

`npm run check`, `cargo test`, `cargo fmt --check`, `npm run format:check`, сборка Tauri. `npm run test:ui:maintenance` выполняет сквозные сценарии в браузерной демонстрации, включая обычные задачи расширений, план и подтверждение, импорт чужой команды, темы и ширины 760–1280. Существующие `test:ui` и `test:ui:features` проверяют регрессии.

`scripts/native-maintenance-smoke.mjs` подключается к специально запущенному тестовому WebView на порту 9231 с пустой изолированной папкой AppDock. Он читает реестр, строит планы, проверяет отказы IPC и демозащиту; **никогда не запускает реальный план и не возобновляет реальную очередь**. Rust-тесты используют временные файлы, в том числе минимальную MSI-базу только с таблицей свойств. Установки, удаления и запись системного / пользовательского PATH на рабочем компьютере для проверки не выполняются.

Параметры WinGet сверены с первичными источниками Microsoft: [uninstall](https://learn.microsoft.com/en-us/windows/package-manager/winget/uninstall), [repair](https://learn.microsoft.com/en-us/windows/package-manager/winget/repair). Фактические возможности установленного CLI дополнительно проверяются через `--help`.
